# Web application house system

Build one coherent product with two deliberately different surfaces:

- **Public surface:** Mizanic/emcp marketing rhythm — wide containers, strong
  typography, 40–48px CTAs, generous sections, real visual hierarchy.
- **Product surface:** emcp application rhythm — compact controls and tables,
  restrained type, persistent shell, dense but never cramped.

Do not apply product density to a landing page. Do not apply landing-page
scale to an admin table.

## Start with the live project

For an existing codebase:

1. Read the nearest `AGENTS.md`, manifests, routes, styles, shared UI, state,
   and tests before proposing changes.
2. Identify whether each route is public, product, or mixed.
3. Audit the current page at desktop and mobile widths when browser tooling is
   available. Record control height, container width, side padding, section
   padding, heading scale, and repeated component variants.
4. Preserve working behavior. Reuse the current component system when it
   already matches this skill; do not create a parallel design system.

For a new project, read `references/scaffold.md` and
`references/design-system.md` before writing files.

## Fixed foundation

| Concern         | Default                                                                       |
| --------------- | ----------------------------------------------------------------------------- |
| Framework       | TanStack Start on Vite, React 19, strict TypeScript                           |
| Routing         | File-based TanStack Router                                                    |
| Server data     | TanStack Query                                                                |
| Tables          | TanStack Table when sorting, selection, pagination, or reusable columns exist |
| Forms           | TanStack Form for validated or multi-field forms; local state for tiny forms  |
| Client UI state | One focused Zustand store by default                                          |
| Styling         | Tailwind CSS v4 with CSS-first semantic tokens                                |
| Components      | Official shadcn/ui registry components, configured with `--base base`         |
| Icons           | Lucide React unless the project already has a deliberate icon system          |
| Fonts           | Bundled Geist Variable + Geist Mono Variable packages                         |
| Validation      | Zod at external boundaries, URL search params, and form schemas               |

Prefer the TanStack solution when it owns the problem. Do not use TanStack
Store in addition to Zustand. Do not add Table, Form, or Virtual merely to
decorate the dependency list.

## Non-negotiable architecture

1. Keep server data in Query, shareable list state in Router search params,
   app-wide UI preferences in Zustand, and short-lived interaction state
   locally.
2. Keep database and secret-bearing imports behind Start server functions or
   a typed external API boundary.
3. Use TanStack Start for public pages too. Prerender eligible public routes;
   keep authenticated routes dynamic.
4. Use semantic component tokens (`bg-background`, `text-muted-foreground`,
   `border-border`, `bg-primary`). Keep status colors behind literal semantic
   maps so Tailwind can detect them.
5. Use `data-theme` before first paint. Ship light and dark tokens; do not
   simulate a second theme with filters.
6. Treat `components/ui` as shared library code. Put product composites and
   marketing composites outside it.

## shadcn boundary

Use shadcn/ui, not an imitation of its conventions:

1. Initialize shadcn through its official CLI with the Base UI option.
2. Add primitives and blocks with `shadcn add`; let the project
   `components.json` select the correct Base UI-backed registry variant.
3. Import UI in routes, features, and composites only from
   `@/components/ui/*`. Never import `@base-ui/react` from application code.
4. Direct Base UI imports may appear inside source generated by shadcn because
   Base UI is the selected internal primitive layer. Do not hand-author a
   replacement wrapper when a shadcn component exists.
5. If the registry lacks a needed component, first compose installed shadcn
   components. Ask before introducing a direct Base UI primitive as a custom
   exception.

Read `references/scaffold.md` for the exact CLI workflow and
`references/components.md` before installing or modifying components.

Read `references/data-layer.md` whenever data, auth, mutations, caching, or
state ownership is involved.

## Visual contract

### Product UI

- Default desktop control: 32px (`h-8`); prominent app action: 36px
  (`h-9`). Keep coarse-pointer/mobile targets at least 44px.
- App shell: 48px top bar, `px-6 py-5` page frame on desktop, smaller padding
  on narrow screens.
- Page title: `text-xl font-semibold`; body: `text-sm`; metadata: `text-xs`.
- Cards and table shells use borders and quiet surface steps. Reserve strong
  shadows for overlays.

### Public UI

- Hero CTA: never reuse the compact app `lg` size. Use 40px for secondary
  public actions and 48px for the primary hero CTA.
- Container: `max-w-6xl` for text-led SaaS pages; `max-w-7xl` for image-led or
  editorial layouts. Do not default a full landing page to `max-w-5xl`.
- Side padding: `px-5 sm:px-6 lg:px-8`.
- Section rhythm: normally 80–96px vertically (`py-20 md:py-24`).
- Hero title: roughly `text-4xl` to `text-6xl/7xl`; section title:
  `text-3xl` to `text-5xl`, chosen by content and hierarchy.
- Use fewer, stronger sections. Avoid a stack of interchangeable icon cards.

Read `references/marketing.md` for public routes and
`references/app-shell.md` for authenticated routes. Read
`references/components.md` before changing primitives or repeated
composites.

## Starter assets

Copy only what the project needs:

```text
assets/styles.css                  -> merge house tokens/utilities into the shadcn CSS file
assets/lib/{utils,colors}.ts       -> src/lib/
assets/store/ui.ts                 -> src/store/ui.ts
assets/hooks/use-mobile.ts         -> src/hooks/
assets/components/ui.tsx           -> src/components/ui-composites.tsx
assets/components/marketing.tsx    -> src/components/marketing/layout.tsx
```

Create `src/components/ui/*` with the shadcn CLI; do not copy a hand-built
primitive set. Preserve imports and base layers written by `shadcn init` when
merging the house stylesheet. Rename storage keys and brand tokens immediately.
The remaining assets are a baseline, not permission to paste every composite
into every project.

## Build sequence

1. Write a route and surface map: public, auth, and product routes.
2. Scaffold the emcp-shaped folder and dependency layout.
3. Establish brand tokens and both theme values before page-level styling.
4. Install the required shadcn components, then apply the house size ladder.
5. Build public shell and app shell separately; share tokens, not density.
6. Wire Query/Router/Zustand ownership before complex pages.
7. Build real states: loading, empty, error, disabled, pending, destructive,
   mobile, and keyboard.
8. Validate the entire flow, not isolated screenshots.

## Quality gate

Before completion:

- Run typecheck, tests, and production build.
- Compare desktop and mobile screenshots against the requested reference
  language.
- Check light and dark reloads for theme flash.
- Verify public CTAs are 40–48px and app controls follow the product scale.
- Check container width, side padding, and section gaps at common breakpoints.
- Verify keyboard focus, Escape behavior, labels, empty/loading/error states,
  and reduced motion.
- Search for duplicate primitives, raw palette classes, server data in
  Zustand, and accidental one-off spacing.
- Search application code outside `components/ui` for direct
  `@base-ui/react` imports; the result must be empty.
