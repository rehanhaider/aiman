# Reference Implementation Playbook — SEO/GEO/AEO patterns

Companion to the seo-expert skill. When the user asks to ship a specific technique (or you've audited and they want to act on a recommendation), pick the matching pattern below and implement it. Thirty numbered entries — each covers what it is, when to recommend it, how to ship it on a typical Astro/static stack (portable to others), and pitfalls — followed by the pitfalls-and-lessons log and stack-specific notes.

### 1. Per-page dynamic OG cards (satori + sharp)

**What:** Render a 1200×630 PNG per page at build time using satori (JSX → SVG) and sharp (SVG → PNG). One template, automatic for every page.

**When:** Site has more than ~20 pages and current `og:image` is a single static fallback. Branded, on-system social previews lift CTR on every share.

**How:**

1. Install: `npm install satori --save-dev` (sharp is usually already present).
2. Bundle a TTF for satori (Montserrat, Inter, or whatever matches the brand) under `web/scripts/fonts/`. One-shot script fetches from Google Fonts repo and commits the file for deterministic builds.
3. Implementation lives in plain ESM (`web/src/lib/og/render.mjs`) so both the Astro endpoint and any standalone scripts can import the same renderer. Add a `render.d.ts` for type info.
4. **Manifest** (`web/src/lib/og/manifest.ts`) enumerates every page that needs an OG card — pull from content collections, programmatic taxonomies, static page list. Slug + canonical path + title + kicker per entry. Use a stable `_root` slug for the home page since `/` doesn't slug cleanly.
5. **Endpoint** at `web/src/pages/og/[...slug].png.ts` with `getStaticPaths` from manifest + `GET()` that returns PNG with long cache header.
6. **Layout fallback**: if no explicit `ogImage` is passed, default `og:image` to `/og/<slug>.png` derived from canonical path. Pages with hand-painted hero images (blog/learn slugs) override.
7. **Test**: assert every sitemap URL's `og:image` resolves to a real PNG in `dist/`. Also assert PNG dimensions are 1200×630 and ≥ 8KB to catch silent satori/sharp render failures.

**Pitfalls:**

- Satori needs explicit fonts — system fonts don't work. Bundle the TTF.
- The `@/` Vite alias does NOT resolve from standalone Node scripts (tsconfig vs config-time). Use relative paths in plugin/script files.
- If the manifest skips a page that Layout still references via fallback, you ship a broken `og:image`. Test catches it.

### 2. Static fallback OG synced with brand

**What:** A static `web/public/og-default.png` that survives if a page doesn't have a dynamic OG card. Generated by the same satori renderer so it's never off-brand.

**When:** Always — even with dynamic OG, you want a sensible fallback in the JSON-LD `image` field of HowTo / Article schemas (which the dynamic OG endpoint can't supply directly to schema).

**How:** Wire a `prebuild` npm script that runs `node scripts/generate-default-og.mjs`, which calls the shared renderer with the home-page copy and writes to `public/og-default.png`. Result is committed; build pipeline keeps it fresh.

**Pitfall:** If you ever duplicate the satori tree in two places (renderer + generator), brand drift starts. Always import from the single .mjs source.

### 3. Logo enhancement (Organization + ImageObject)

**What:** Google's [Logo enhancement](https://developers.google.com/search/docs/appearance/logos) — the brand logo can appear in Knowledge Panel and brand searches.

**When:** Always. Cost is one PNG file + ~10 lines of JSON-LD.

**How:**

1. Generate `public/logo.png` — must be **PNG/JPG/WebP** (NOT SVG — Google rejects SVG for Logo). Minimum 112×112; 512×512 recommended.
2. On the home page, emit `Organization` JSON-LD with:
   ```json
   {
     "@context": "https://schema.org",
     "@type": "Organization",
     "@id": "https://example.com/#organization",
     "name": "...",
     "url": "https://example.com",
     "logo": {
       "@type": "ImageObject",
       "url": "https://example.com/logo.png",
       "contentUrl": "https://example.com/logo.png",
       "width": 512,
       "height": 512,
       "caption": "Brand logo"
     }
   }
   ```
3. Add `sameAs[]` array if the brand has any social/GitHub presence — strengthens entity verification.

**Pitfall:** Don't reference an SVG. Google's Logo enhancement explicitly rejects vector formats. Use a small Node script (`scripts/generate-logo-png.mjs`) with `sharp` to rasterize the SVG once and commit the PNG.

### 4. Article schema with full publisher + author + image

**What:** Article (or BlogPosting / NewsArticle) JSON-LD with every field Google expects for Article rich-result eligibility.

**When:** Every blog post and editorial article.

**How:** Build a `buildArticleJsonLd()` helper that emits:

```json
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "...",
  "description": "...",
  "url": "...",
  "mainEntityOfPage": { "@type": "WebPage", "@id": "..." },
  "datePublished": "ISO 8601",
  "dateModified": "ISO 8601",
  "image": ["https://.../hero.png"],
  "author": {
    "@type": "Person",
    "@id": "https://.../author/jane#person",
    "name": "Jane Doe",
    "url": "https://.../author/jane",
    "sameAs": ["https://github.com/jane", "https://linkedin.com/in/jane"],
    "jobTitle": "...",
    "image": "..."
  },
  "publisher": {
    "@type": "Organization",
    "@id": "https://.../#organization",
    "name": "...",
    "logo": { "@type": "ImageObject", "url": ".../logo.png", "width": 512, "height": 512 }
  },
  "keywords": ["..."],
  "speakable": { "@type": "SpeakableSpecification", "cssSelector": ["[data-speakable]"] }
}
```

Critical fields: `publisher.logo` as `ImageObject` (not URL string), `image` array, `mainEntityOfPage` as typed object (not bare string), Person author with stable `@id`.

**Pitfall:** Falling back to `og-default.png` for every article's `image` is what blocks rich-result eligibility. Each post needs a real image. If you can't generate per-post images, at least generate a satori card per post and use that.

### 5. HowTo enrichment

**What:** Full HowTo JSON-LD with `totalTime`, `tool[]`, `supply[]`, `estimatedCost: MonetaryAmount`, plus `HowToStep` entries.

**When:** Any page with step-by-step instructions.

**How:** Helper:

```ts
buildHowToJsonLd({
    name: "How to ...",
    description: "...",
    url: canonicalUrl,
    image: "/og-default.png",
    totalTime: "PT1M",  // ISO 8601 duration
    estimatedCost: { currency: "USD", value: "0" },
    tool: ["Web browser"],
    supply: ["Input data"],
    steps: [{ title: "...", description: "..." }, ...]
})
```

The `MonetaryAmount` type for `estimatedCost` is required for richest rich-result eligibility (even at value 0).

**Caveat:** Google removed HowTo rich results from SERP rendering in late 2023 (mobile Sep 2023, desktop Dec 2023). Schema still:
- ✅ Valid (Search Console "Enhancements" still parses)
- ✅ Used by Bing
- ✅ Parsed by Perplexity / ChatGPT / Gemini / Claude
- ✅ Content-understanding signal on Google
- 🔄 May be reinstated (Google has reversed deprecations before)

So ship it; just don't expect the visual carousel on Google SERPs.

### 6. WebSite + SearchAction (Sitelinks Search Box)

**What:** Tells Google your site has internal search. Powers the [Sitelinks Search Box](https://developers.google.com/search/docs/appearance/structured-data/sitelinks-searchbox).

**When:** Site has a real `/search` page (or you're building one). Pure schema without working search will be ignored or even penalized.

**How:** On home page WebSite JSON-LD:

```json
{
  "@type": "WebSite",
  "url": "https://example.com",
  "potentialAction": {
    "@type": "SearchAction",
    "target": {
      "@type": "EntryPoint",
      "urlTemplate": "https://example.com/search?q={search_term_string}"
    },
    "query-input": "required name=search_term_string"
  }
}
```

Then build `/search` (see playbook §13).

**Caveat:** Google deprecated Sitelinks Search Box for new sites in May 2024. Existing implementations still work; new ones may not render. Schema is harmless and AI engines still parse it as a structural hint.

### 7. RSS + JSON Feed for blogs/learn hubs

**What:** Feeds let readers, RSS aggregators, AI crawlers (Perplexity/ChatGPT) ingest content efficiently.

**How:**

1. Install `@astrojs/rss`.
2. Endpoint at `src/pages/blog/feed.xml.ts` returns RSS via `rss({ title, description, items: [...] })`. One per content collection.
3. Endpoint at `src/pages/blog/feed.json.ts` returns JSON Feed 1.1 manually (no helper needed — it's just a JSON object with the right shape).
4. In `Layout.astro` `<head>`, add `<link rel="alternate" type="application/rss+xml" href="/blog/feed.xml" />` site-wide so feed readers auto-discover.

**Test:** assert each feed contains every non-draft post URL from the collection.

### 8. llms.txt + llms-full.txt

**What:** [llms.txt](https://llmstxt.org) is the GEO equivalent of robots.txt — a curated markdown index telling AI crawlers which pages matter most.

**When:** Always. Zero risk, real upside on Perplexity/ChatGPT/Gemini ingestion.

**How:**

1. Generate dynamically via Astro endpoint at `src/pages/llms.txt.ts` that reads from content collections + page generators. Returns `Content-Type: text/plain`.
2. Structure: `# Site name`, blockquote tagline, sections with markdown links (`- [Title](url): description`).
3. Sections to include: Generator/Tool routes, Learn (long-form guides), Blog, Use-case guides, Feeds & data, About + policies, **Key facts** (a few bullet points AI engines can lift verbatim).
4. Also create `src/pages/llms-full.txt.ts` — concatenate the full body of every editorial post for LLM ingestion.
5. Reference both in `robots.txt` as comments: `# Curated index: https://example.com/llms.txt`.

**Pitfall:** Don't promise things in `llms.txt` that aren't true (e.g. "free forever") — AI engines will quote you, and freemium launches make it a rug-pull.

### 9. Sitemap with content-driven lastmod

**What:** `<lastmod>` tells Google "re-crawl this page" — the actual freshness signal.

**How:**

1. Use `@astrojs/sitemap` with `serialize` callback.
2. Build a `Map<canonicalPath, ISO date>` from content collection frontmatter at config-time (`buildLastModMap.mjs`). Read each `.md` file, regex-extract `updatedDate ?? publishDate`.
3. In `serialize`, look up the path in the map; fall back to `buildLastMod` (current build date) for non-collection pages.

**Pitfall:** Build date as fallback for everything makes lastmod meaningless. Specifically pull from `updatedDate` on editorial posts.

### 10. Tag/category archives

**What:** Auto-generated `/blog/tag/<tag>` and `/learn/tag/<tag>` pages from frontmatter tags. Massive internal-linking lift, $0 content cost.

**When:** Any time content has a `tags[]` field that's used in frontmatter but not surfaced as navigable archives.

**How:**

1. Helper: `slugifyTag()`, `collectTags()` returning `Map<slug, {display, posts[]}>`, `allTagsSorted()` for the index.
2. `pages/blog/tag/[tag].astro` with `getStaticPaths` enumerating distinct tags.
3. `pages/blog/tag/index.astro` listing all tags with post counts.
4. Update card components: tag chips link to `/blog/tag/<slug>`. Add `data-speakable` to title only, not chips.
5. Tag pages emit `WebPage` + `BreadcrumbList` + `ItemList` JSON-LD.
6. Add to OG manifest + search index.
7. Add a "Browse by tag" CTA in the `/blog` and `/learn` hub headers.

**Pitfall:** Tag-page URLs collide with sibling slug routes — tighten slug-page test helpers to exclude `/blog/tag` from "is this a post?" checks.

### 11. Glossary hub with DefinedTermSet schema

**What:** A single page with definitions of every domain term, each with an anchor ID and structured data.

**When:** Site covers a technical or specialized domain where readers benefit from term definitions. Becomes an entity hub for AI search.

**How:**

1. `lib/glossary/manifest.ts` — typed term list: `{ slug, term, category, definition, related?[] }`. Aim for 30-40 terms.
2. `pages/learn/glossary.astro` — render terms grouped by category. Each term gets `<dt><span id={slug}>...</span><a href="#{slug}">#{slug}</a></dt><dd>{definition}</dd>`.
3. JSON-LD: emit one `DefinedTermSet` containing array of `DefinedTerm` blocks (one per term, each with stable `@id` URL fragment).
4. Add the glossary to OG manifest, search index, `/learn` hub header.
5. Test: every term in DefinedTermSet has a matching anchor element in the rendered HTML.

**Pitfall:** Don't auto-link glossary terms within the glossary itself (recursive). Ensure the auto-link plugin (§14) only runs on markdown content, not on `.astro` template pages.

### 12. Auto-link plugin (rehype) for glossary cross-references

**What:** Walk markdown body content; auto-replace first occurrence of each glossary term with a link to `/learn/glossary#<slug>`. Each term linked at most once per page. Skip headings/code/existing-links.

**When:** Site has a glossary AND substantial editorial content. Multiplies the glossary's value.

**How:**

1. Create `web/src/plugins/rehype-glossary-autolink.ts`. Use `unist-util-visit` to walk the hast tree.
2. Build matchers from `GLOSSARY_TERMS` — strip parenthetical content from term names; extract acronyms separately.
3. Skip tags: `a`, `code`, `pre`, `script`, `style`, `noscript`, `h1`-`h6`, `dt`, `dd`.
4. Skip single-word terms shorter than ~5 chars (avoids PNG/SVG/JPG/GS1/DPI/PPI spam).
5. Track linked slugs per page; bail after first link per term.
6. Wrap match in `<a class="auto-glossary-link" data-glossary-link="true" href="/learn/glossary#<slug>">`.
7. Register in `astro.config.mjs` under `markdown.rehypePlugins: [rehypeGlossaryAutolink]`.
8. Add subtle CSS (dotted underline + cursor: help) so auto-links visually differ from author-placed links.
9. Tests: every learn post has ≥1 auto-link; no auto-link inside skip-tags; each slug at most once per page.

**Pitfall:** Use relative imports from the plugin (`../lib/glossary/manifest`) — Vite alias `@/` doesn't resolve from config-time plugin loaders.

### 13. Internal /search page

**What:** A `/search` page that filters site content client-side from a baked-in JSON index, paired with the `WebSite.SearchAction` schema (§6).

**How:**

1. `lib/search/manifest.ts` — `buildSearchIndex()` enumerates every indexable page with `{url, title, description, section}`. For glossary, emit one entry per term targeting `/learn/glossary#<slug>`.
2. `pages/search.astro`:
   - Loads index server-side.
   - Renders all entries grouped by section as the no-JS fallback.
   - Inlines the index as `<script type="application/json" id="search-index">`.
   - Inline `<script is:inline>` reads `?q=` from URL, filters by tokenized AND match against title + description + section.
   - Form submits to `/search` so URL stays in sync.
3. Add a magnifying-glass link to the global header.
4. Test: every sitemap URL appears in the inline index; SearchAction on home references this page.

**Pitfall:** ~50KB inline JSON is fine for sites under ~1000 pages. Beyond that, switch to a separate fetched `/search-index.json` with cache headers.

### 14. Author content collection + ProfilePage

**What:** First-class author entity + per-author page emitting `Person` + `ProfilePage` JSON-LD with `sameAs[]`.

**When:** Editorial site with one or more named authors. Critical for E-E-A-T on YMYL-adjacent content; nice-to-have on tool sites.

**How:**

1. `authors` content collection in `content.config.ts` with Zod schema: `name, jobTitle, location, bio, avatar (image()), website (url), sameAs[]`.
2. One markdown file per author at `content/authors/<slug>.md` with frontmatter + a short markdown bio body.
3. `pages/author/[slug].astro` — render avatar + bio + sameAs chips + lists of authored posts. Emit `ProfilePage` containing nested `Person` with `@id` ending `#person`, plus a separate `Person` block for clarity.
4. `lib/authors.ts` — `resolvePostAuthor()` looks up an author entry by name; falls back to the default author entry when the post's frontmatter author string doesn't match (so every post gets a Person byline, not Organization).
5. `AuthorByline.astro` component — renders avatar + name + job title + dates on slug pages, links to `/author/<slug>`.
6. Update `buildArticleJsonLd` to accept Person author with `sameAs[]`.

**Pitfall:** Don't put a real-name byline on programmatic / templated pSEO pages — Google's "scaled content abuse" policy flags ~150-page templated content with the same byline. Editorial only.

### 15. Speakable schema

**What:** `SpeakableSpecification` with `cssSelector` tells voice assistants and AI Overviews which parts of a page are quotable.

**How:**

1. Add `data-speakable` attribute to H1 + summary paragraph on editorial pages.
2. Helper: `buildSpeakableSpecification({ cssSelector: ["[data-speakable]"] })`.
3. Pass `speakable: true` in `buildArticleJsonLd` and `buildWebPageJsonLd` to emit it.
4. Test: schema's `cssSelector` resolves to ≥2 elements in the rendered HTML (catches drift between schema and DOM).

**Pitfall:** Don't mark every paragraph speakable. Pick the headline + a single summary line. Too broad = "everything is important" = nothing is.

### 16. Article-typed OG meta

**What:** `<meta property="article:published_time">`, `:modified_time`, `:author`, `:tag`, `:section`. Facebook/LinkedIn/AI agents read these.

**How:** Layout accepts optional `articlePublishedTime`, `articleModifiedTime`, `articleAuthor` (string or array), `articleTags[]`, `articleSection` props. Render only when `ogType === "article"`.

**Test:** non-article pages should emit zero `article:` meta tags (catches accidental site-wide leaks).

### 17. Per-post hero images + responsive variants

**What:** Per-post heroImage in frontmatter; rendered with Astro's `<Image>` component for automatic WebP + responsive variants.

**How:**

1. Add `heroImage: image().optional()` to the content collection's Zod schema.
2. Save images to `web/src/assets/<collection>/<slug>.png` (NOT `public/` — Astro's image pipeline only optimizes assets under `src/`).
3. Render with `<Image src={post.data.heroImage} alt={...} widths={[480, 720, 768, 1536]} sizes="(min-width: 768px) 768px, 100vw" quality={82} format="webp" loading="eager" fetchpriority="high" />` for above-fold heroes.
4. Pass `heroImage.src` to `buildArticleJsonLd({image})` and to Layout's `ogImage` prop. Pass `heroImage.width` + `.height` to Layout's `ogImageWidth` + `ogImageHeight`.

**Pitfall:** `loading="lazy"` on a hero image kills LCP. Eager + fetchpriority high for hero; lazy for thumbnails on cards.

### 18. Outbound authoritative citations

**What:** Append a `## Sources` section to every long-form editorial post with 2-4 links to authoritative external sources (Wikipedia, ISO, IETF RFCs, official primary sources, peer-reviewed research).

**When:** Any explainer, how-to, or reference content. Required for E-E-A-T on YMYL-adjacent topics; valuable on tool/utility content too.

**How:** Build a per-slug citations manifest mapping each post to 2-4 hand-picked stable URLs with one-line context notes. Run a script (`scripts/append-citations.mjs`) that idempotently appends `## Sources` to each markdown file.

**Test:** every editorial post page renders ≥2 outbound `<a>` tags pointing at an allowlist of authoritative domains (Wikipedia, ISO, IETF, etc.).

**Pitfall:**

- Stick to high-stability URLs. No SEO blogs, no aggregator sites, no shortened URLs, no paywalled sources.
- Don't auto-generate citations from a vague topic match — they look fake. Hand-pick or skip.

### 19. Programmatic SEO (pSEO) with indexation heuristics

**What:** Auto-generate pages from a taxonomy (e.g., industry × use-case, keyword × format). Each page has unique-enough copy + rich schema.

**When:** Site targets a domain with combinatorial intent (industry × action, location × service, problem × tool). Real query volume across the matrix.

**How:**

1. Define canonical taxonomy lists (`PROGRAMMATIC_INDUSTRIES`, `PROGRAMMATIC_USE_CASES`, etc.) as TypeScript arrays.
2. Generator function builds `ProgrammaticPage` objects per allowed combination with title/description/h1/intro/benefits/steps/pitfalls/faqs.
3. **Indexation heuristics** (`getProgrammaticIndexationDecision()`): mark thin, low-intent, or duplicate pages as `noindex` with canonical pointing at the strongest covering page. Returns `{indexable, canonicalPath, reason}`.
4. Emit only indexable pages in sitemap; render every page (so canonical works) but include `noindex` meta on suppressed ones.
5. Each page emits `HowTo` + `FAQPage` + `BreadcrumbList` schema.
6. Test: every indexable page emits enriched HowTo + FAQPage with the right field shape.

**Pitfall:** Don't add author bylines to pSEO pages — looks like scaled content abuse. Use Org-level attribution (footer) instead.

### 20. "How to scan/install/setup on [device]" pSEO

**What:** Device-family content matching exact-match queries like "how to scan QR on iPhone", "how to install X on Android", etc.

**When:** Site has a tool or product where users frequently search "how to [verb] on [device]". Massive query volume, low competition.

**How:** Treat as a small pSEO matrix with hand-written content per device (not template-generated — the differences between iPhone vs Samsung vs older Android are substantive). Each page: device name, OS requirement, primary method, 3-5 numbered steps, pitfalls, 3-5 FAQs, related-device links. HowTo + FAQPage + BreadcrumbList schema.

**Pitfall:** Don't add a generic "Camera app" entry — the platforms differ enough that a single page would underserve every query. Per-device specificity is the SEO win.

### 21. Comparison pages

**What:** `/compare/<your-product>-vs-<competitor>` BOFU pages.

**When:** **High caution.** Only after your product is in market and you can be honest about diff tables. Pre-paid-tier risk: you're often about to be the thing being compared.

**How:** Hand-written; avoid auto-generation. Honest diff tables; no hatchet jobs. Schema: `Article` + `BreadcrumbList`.

**Pitfall:** If your own pricing isn't settled, comparison pages can box you in. Defer until launch.

### 22. Sitelinks-friendly internal navigation

**What:** Google sometimes shows multiple "sitelinks" under a brand-search SERP entry. Internal navigation, breadcrumbs, and stable site structure feed this.

**How:**

- Visible breadcrumbs on every page below home, paired with `BreadcrumbList` JSON-LD.
- Header navigation that consistently surfaces the top-level sections (blog, learn, glossary, search, etc.).
- Hub pages with `ItemList` schema enumerating their children.

### 23. Comprehensive regression-testing pattern

**What:** vitest + cheerio against `web/dist/` after `astro build`. Walks the sitemap and asserts every URL has the schemas, meta tags, and assets it should.

**When:** Once you've shipped 3+ structured-data patterns. Schema is fragile — a refactor that drops one type goes unnoticed without tests.

**How:** Test files like:

- `test_metadata.test.ts` — every sitemap URL has title/description/canonical/OG tags + valid JSON-LD.
- `test_structured_data.test.ts` — Article/Logo/HowTo/Breadcrumbs spot-checks.
- `test_seo_guards.test.ts` — full home-page schema set; loops over every pSEO route family asserting enrichment.
- `test_dynamic_og.test.ts` — every sitemap URL's `og:image` resolves to a real file in dist.
- `test_feeds_and_llms.test.ts` — feeds + llms.txt + alternate links.
- `test_authors_and_lastmod.test.ts` — Person schema + sitemap lastmod.
- `test_search.test.ts` — /search index covers everything; SearchAction valid.
- `test_speakable.test.ts` — Speakable selectors match DOM.
- `test_auto_glossary_link.test.ts` — auto-link rules + skip behavior.
- `test_outbound_citations.test.ts` — every learn post has ≥2 authoritative outbound links.
- `test_article_og.test.ts` — `article:` meta on slugs only.
- `test_tags.test.ts` — tag archives + chip URLs.
- `test_glossary.test.ts` — DefinedTermSet + anchor matching.
- `test_scan_guides.test.ts` — device-family pSEO coverage.

Bump test timeouts to 30s on tests that walk the full sitemap (default 5s isn't enough past ~200 pages).

### 24. Hosting/framework URL-policy alignment (trailing slash, cleanUrls)

**What:** Make the framework emit URLs in exactly the style the host serves. The invariant: sitemap `<loc>` == canonical == `og:url` == final served URL, HTTP 200, zero redirects.

**When:** Always verify on existing sites; mandatory on any migration. This mismatch caused a full-site deindexing on cloudbytes.dev (May 2026): Astro emitted trailing-slash URLs while Firebase Hosting (`trailingSlash: false`) 301'd them all, so Googlebot saw sitemap → 301 → page whose canonical pointed back at the redirecting URL.

**How (Astro + Firebase example):**

1. Read the host policy (`firebase.json`: `cleanUrls`, `trailingSlash`).
2. Match the framework: `trailingSlash: "never"` (or `"always"`) in `astro.config.mjs` — never leave the default `"ignore"` on a host with an opinion.
3. Canonical builders need a root-URL guard: `new URL("/", site).toString()` re-adds the slash, so strip with `.replace(/\/+$/, "")`.
4. Sweep internal links, pagination hrefs, feed item URLs, and JSON-LD `@id`/`url` fields for the wrong style.
5. Regression test: walk the built sitemap and assert no `<loc>` has a trailing slash (or all do), and canonical === sitemap loc **without normalizing** — normalized comparisons hide exactly this bug.

**Pitfall:** dist-level tests can't catch it — the redirect happens at the hosting layer. Pair with the prod smoke test (§30).

### 25. Legacy sitemap + feed redirects after migration

**What:** 301s for every well-known URL the old platform emitted that the new one doesn't.

**When:** Every platform migration, immediately, in the same deploy.

**How (firebase.json example):**

```json
{ "source": "/sitemap.xml", "destination": "/sitemap-index.xml", "type": 301 },
{ "source": "/feeds/**", "destination": "/rss.xml", "type": 301 }
```

Common legacy names: `/sitemap.xml` (Pelican/Jekyll/Hugo default vs. `@astrojs/sitemap`'s `/sitemap-index.xml`), `/feeds/all.atom.xml` + `/feeds/<category>.atom.xml` (Pelican), `/feed/` (WordPress), `/atom.xml`, `/index.xml` (Hugo). Then update robots.txt, resubmit in GSC, and delete the stale sitemap submission.

**Pitfall:** GSC keeps fetching the old sitemap URL for years after submission. A 404 there isn't fatal by itself, but during a migration it removes your discovery channel at the exact moment everything else changed.

### 26. VideoObject schema for embedded videos

**What:** `VideoObject` JSON-LD for pages embedding video (YouTube or self-hosted) — name, description, `thumbnailUrl`, `uploadDate`, `embedUrl`. Eligibility for video rich results and video indexing.

**When:** Any post with a video embed (e.g. a `youtubeId` frontmatter field) that currently emits only Article schema.

**How:** Add a `buildVideoObject()` helper; for YouTube, `thumbnailUrl` is `https://i.ytimg.com/vi/<id>/hqdefault.jpg` and `embedUrl` is the nocookie embed URL. Emit alongside the Article node in the same graph. Test: every page with an embed has exactly one VideoObject with the four required fields.

**Pitfall:** Don't emit VideoObject when the video isn't the page's main content focus — Google may ignore it; the schema should describe a real, visible embed.

### 27. Immutable cache headers for hashed assets

**What:** `Cache-Control: public, max-age=31536000, immutable` for build-hashed assets (e.g. Astro's `/_astro/**`).

**When:** Any static host where the framework fingerprints filenames. Repeat-visit CWV (and crawl efficiency) improve for free.

**How (firebase.json):**

```json
{ "source": "/_astro/**", "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }] }
```

Keep short TTLs only for unfingerprinted files (images under stable names, `404.html`).

### 28. Video embed facades (CWV)

**What:** Replace eager third-party video iframes with a thumbnail facade that swaps in the iframe on click (`lite-youtube-embed` or a ~20-line inline script).

**When:** Any above-the-fold YouTube embed — an eager `youtube-nocookie.com` iframe (worse with `autoplay`) pulls hundreds of KB of third-party JS before LCP and damages INP.

**How:** Render `<img src="https://i.ytimg.com/vi/<id>/hqdefault.jpg">` + play button; on click, replace with the real iframe. Keep `loading="eager"` only for the thumbnail image. Pairs with §26 (the VideoObject stays valid — `embedUrl` doesn't require an eager iframe).

### 29. Content decay refresh program

**What:** A standing process for refreshing or pruning aging posts instead of only writing new ones.

**When:** Sites older than ~2 years where legacy posts hold most of the traffic.

**How:**

1. From GSC, list pages whose impressions fell >40% year-over-year (decay candidates).
2. For each: refresh (update versions/commands/screenshots, record via `updatedDate` frontmatter so sitemap lastmod and `article:modified_time` move), consolidate (301 into a stronger sibling covering the same intent), or retire (410 + remove from sitemap) — in that order of preference.
3. Don't version-pin titles ("Upgrade to Python 3.9") — say "latest version" in the title and pin versions in the body, so the title doesn't expire.
4. `updatedDate` discipline: only bump on real content changes; a visible "Last updated" line in the body should mirror frontmatter, not replace it.

**Pitfall:** Mass-updating `lastmod` without content changes teaches Google to ignore your lastmod entirely.

### 30. Post-deploy production smoke test

**What:** A tiny CI job that runs against the **live site** after deploy: fetch robots.txt and the sitemap, sample N sitemap URLs, assert HTTP 200 with no redirect and `rel=canonical` equal to the fetched URL.

**When:** Any site that has ever been bitten by a hosting-layer/framework mismatch — dist tests validate HTML, not serving behavior.

**How:** ~30 lines of Node in a post-deploy workflow step: `curl -sI` (or fetch) the sitemap, parse 5–10 `<loc>` values, fail the job on any 3xx/4xx or canonical mismatch. Alert, don't silently log.

## Pitfalls & Lessons Learned

These are repeated mistakes that an audit should flag, and that an implementation should avoid:

### Schema / structured data

- **HowTo rich results were deprecated by Google in late 2023.** Schema is still valid; ship it for Bing + AI engines + future reinstatement, but don't promise the user a visual rich result on Google SERPs.
- **Google's Rich Results Test only shows rich-result-eligible types** (FAQ, Article, WebApplication, Breadcrumb). It hides Organization, WebSite, HowTo. Use [validator.schema.org](https://validator.schema.org) to see the full graph.
- **Logo enhancement requires PNG, not SVG.** Google explicitly rejects vector formats for the Logo signal.
- **`publisher.logo` must be `ImageObject` with width/height**, not a URL string. Article rich-result eligibility is gated on this.
- **`mainEntityOfPage` should be a typed object** (`{"@type": "WebPage", "@id": url}`), not a bare string. Both are valid; the typed form is preferred.
- **Each Person/Organization needs a stable `@id`** — same identifier across all pages where that entity appears. Without it, Google treats them as separate entities.

### Pricing / positioning copy

- **"Free forever" / "always free" / "never charge" lock pricing.** If the site might launch a paid tier, those phrases become rug-pulls. Use "Free generator" / "free with no signup" — describe today's reality, not a permanent commitment.
- **Privacy claims should be architectural, not pricing-tier-bound.** "The free generator runs in your browser" survives a freemium launch (the paid tier can do server-side dynamic features without contradicting). "We never collect data" doesn't.
- **Pre-disclose freemium honestly in `llms.txt` Key Facts** so AI engines don't spread "always free" misinformation that you'd later have to walk back.

### Content quality / scale

- **Don't put real-name bylines on programmatic pSEO pages.** Google's scaled content abuse policy flags ~150 templated pages with the same byline. Editorial bylines + Org footer attribution on pSEO is the right split.
- **Don't fabricate Person bylines with no real profiles.** A pseudonymous author with no LinkedIn/GitHub/etc. presence is *worse* than no byline — Google detects the absence.
- **Single-word acronyms shouldn't be auto-linked** (PNG, SVG, JPG, GS1, DPI). They appear too often in technical writing and create link spam.
- **Speakable on too many elements signals nothing.** One headline + one summary per page.

### URL / routing

- **`/blog/tag` and similar collide with `/blog/<slug>` regex matchers.** Tighten test helpers to exclude tag/glossary/scan paths.
- **Astro endpoint URLs must match what the Layout's OG fallback expects.** If Layout computes `/og/<slug>.png` but the manifest doesn't include that slug, you ship a 404 OG image. Add a sitemap-walk test asserting every `og:image` URL exists in dist.

### Migrations / hosting / recovery

- **The framework's default trailing-slash behavior is a deindexing vector.** If the host serves slashless URLs and the framework emits slashed ones (or vice versa), every sitemap entry becomes a 301 and every canonical points at a redirect. Google's verdict is "Page with redirect" → dropped. Align `trailingSlash` explicitly (§24) and test the invariant without normalizing URLs.
- **Sitemap filenames are part of your public API.** Renaming `/sitemap.xml` to `/sitemap-index.xml` without a 301 + robots.txt update + GSC resubmission silently severs discovery. Same for feed URLs.
- **Redirect chains dilute and slow signal transfer.** old-old → old → new must be collapsed so every historical URL reaches the final destination in one hop. Audit with `curl -sIL`.
- **Dist-level tests pass while production fails.** Build-output tests can't see hosting-layer redirects, headers, or cleanUrls behavior. Only a post-deploy smoke test against the live site (§30) closes that gap.
- **A deindexed page doesn't bounce back when the bug does.** Expect recrawl in 2–6 weeks and rank recovery in 4–12; impressions lead clicks. Verify with URL Inspection (crawl date after the fix, canonical match) before assuming something is still broken — and don't change slugs/titles/H1s mid-recovery.
- **lastmod-on-every-deploy is the same as no lastmod.** Falling back to the build timestamp for all pages teaches Google to distrust the signal; drive it from content dates and let only genuinely-changed pages move.

### Astro-specific

- **The `@/` Vite alias works in Vite-resolved code (Astro pages, components, libs)** but does NOT resolve from standalone Node scripts or rehype/remark plugins loaded at config time. Use relative paths (`../lib/...`) in plugin/script files.
- **Renderer code that needs to be shared between an Astro endpoint and a standalone Node script should live as `.mjs`** (plain ESM), with a sibling `.d.ts` for type info. TypeScript imports resolve fine; Node imports require no transpilation.
- **Astro's `<Image>` component only optimizes assets under `src/`.** Static `public/` images are served as-is — useful for logo, robots.txt, og-default.png; not useful for per-post heroes.
- **`loading="lazy"` on the hero image kills LCP.** Use `loading="eager"` and `fetchpriority="high"` for above-fold images.

### AI-search specific

- **`llms.txt` content gets quoted verbatim by AI engines.** Don't put marketing fluff in it. Stick to factual descriptions of pages.
- **Speakable + DefinedTerm work together.** Speakable tells AI "quote this"; DefinedTerm tells AI "this is a citable entity." Both are needed for rich AI-search citation.
- **Outbound citations to canonical sources signal alignment** — when an AI engine compares your content to its sources and sees you link to the same Wikipedia/ISO/RFC pages, it boosts your citability.

## Stack-Specific Implementation Notes

These apply to Astro 6+ static-site projects (the most common stack you'll be implementing on):

- **Content collections** — define schemas with Zod. Use `image()` for typed asset references (returns `ImageMetadata` with `.src/.width/.height`).
- **`<Image>` component** — `widths={[...]}` for srcset variants, `sizes="..."` for browser hint, `quality={82}` is a sane default, `format="webp"` for size, `loading="eager"` + `fetchpriority="high"` for above-fold.
- **API endpoints** — `.ts` or `.mjs` files in `pages/` exporting `GET()` produce static files at build. Use for feeds, llms.txt, OG cards, sitemaps that need code.
- **`@astrojs/sitemap`** — `serialize` callback for per-URL `lastmod`, `filter` to exclude paths.
- **`@astrojs/rss`** — `rss({ title, description, items, customData })` returns a `Response`. JSON Feed needs a hand-rolled `Response` (no helper).
- **`markdown.rehypePlugins`** in `astro.config.mjs` — register rehype plugins for transforms (auto-link, footnote, etc.). Use relative imports.
- **`getStaticPaths`** + `props` — pass complex data to the page template at build time. Endpoint pattern works the same way.
- **`@/` import alias** — works in Astro/Vite-resolved code only. Plugins and standalone scripts use relative paths.
- **Typed JSON-LD helpers** — centralize in `lib/seo.ts`: `buildArticleJsonLd`, `buildHowToJsonLd`, `buildFaqJsonLd`, `buildBreadcrumbJsonLd`, `buildWebPageJsonLd`, `buildSpeakableSpecification`. Keeps schema consistent and testable.
