# Local database (Drizzle + expo-sqlite)

Load this **only if the project already uses (or genuinely needs) a local SQLite database**. Most Expo apps don't. For a typical "talk to a remote API" app, React Query alone covers data, and Zustand + MMKV covers settings. Reach for SQLite when the app must:

- work fully offline against structured data,
- store relational data with joins, cascades, and indexes,
- drive UI that re-renders whenever the database changes (live queries).

The stack is **Drizzle ORM** + **`expo-sqlite`**. Drizzle gives typed schemas, a typed query builder, and `drizzle-kit` for migration generation. `expo-sqlite` provides the SQLite connection plus a built-in change-listener that powers live queries.

## When *not* to reach for this

- A small blob (settings, auth tokens, a few flags) → Zustand + MMKV (`references/storage-hooks.md`).
- A remote API cache → React Query alone — its cache covers staleness, invalidation, optimistic updates.
- A handful of records that rarely join → a JSON blob in MMKV stays simpler.

Surface the trade-off if the user is reaching for SQLite without one of the conditions above; it adds boot-time migrations, a babel/inline-import question, and a manual changelog.

## File layout

```
mobile/
├── drizzle.config.ts        # drizzle-kit config
├── drizzle/                 # generated by `drizzle-kit generate`
│   ├── meta/_journal.json
│   └── 0000_<tag>.sql       # one file per migration
├── db/
│   ├── schema.ts            # table + relation definitions
│   ├── client.ts            # openDatabaseSync() + drizzle() — exports `db`
│   └── migrations.ts        # imports the generated .sql via inlining
└── src/db/
    └── live.ts              # cross-table live-query hook
```

`db/` sits next to `src/`, not inside it. That keeps the schema files near `drizzle.config.ts`, outside the Tailwind content glob, and avoids accidentally scanning the generated SQL. The cross-table live-query hook is React code, so it lives under `src/db/` and is reachable via the `@/db/...` alias.

## drizzle-kit config

```ts
// drizzle.config.ts
import { defineConfig } from "drizzle-kit";

export default defineConfig({
    dialect: "sqlite",
    driver: "expo",
    schema: "./db/schema.ts",
    out: "./drizzle",
});
```

`driver: "expo"` is the load-bearing line — it tells drizzle-kit to emit Expo-flavored migrations consumable by `drizzle-orm/expo-sqlite`.

## Schema

Use `sqliteTable` with column helpers from `drizzle-orm/sqlite-core`. Add explicit indexes for any column the app filters on, and `references(...).onDelete("cascade")` wherever a child row should disappear with its parent.

```ts
import { relations } from "drizzle-orm";
import { index, integer, sqliteTable, text, uniqueIndex } from "drizzle-orm/sqlite-core";

export const items = sqliteTable(
    "items",
    {
        id: text("id").primaryKey(),
        sourceUrl: text("source_url").notNull(),
        savedAt: integer("saved_at").notNull(),
    },
    (t) => ({
        bySaved: index("idx_items_saved").on(t.savedAt),
        bySource: uniqueIndex("uq_items_source").on(t.sourceUrl),
    }),
);

export const media = sqliteTable("media", {
    id: integer("id").primaryKey({ autoIncrement: true }),
    itemId: text("item_id")
        .notNull()
        .references(() => items.id, { onDelete: "cascade" }),
    kind: text("kind").notNull(),
});

export const itemsRelations = relations(items, ({ many }) => ({ media: many(media) }));
```

Relations are optional for raw SQL queries, but required if you want `db.query.items.findMany({ with: { media: true } })` to work.

## Client + PRAGMAs

```ts
// db/client.ts
import { drizzle } from "drizzle-orm/expo-sqlite";
import { openDatabaseSync } from "expo-sqlite";
import * as schema from "./schema";

const expo = openDatabaseSync("app.db", { enableChangeListener: true });

// Neither PRAGMA is on by default — SQLite ships conservative.
expo.execSync("PRAGMA foreign_keys = ON;");
expo.execSync("PRAGMA journal_mode = WAL;");

export const db = drizzle(expo, { schema });
```

Three settings worth understanding:

- **`enableChangeListener: true`** — required for `addDatabaseChangeListener`, which is what powers `useLiveQuery` and `useLiveTables`. Off by default; if you forget it, live queries silently never fire.
- **`PRAGMA foreign_keys = ON`** — SQLite disables FK enforcement per connection. Without this, `onDelete("cascade")` quietly does nothing and orphans accumulate.
- **`PRAGMA journal_mode = WAL`** — write-ahead log. Readers don't block writers; better concurrency on mobile.

## Migrations

Run `npx drizzle-kit generate` after every schema change. It writes a new `drizzle/<idx>_<tag>.sql` and appends to `drizzle/meta/_journal.json`. To execute them at app start, call `useMigrations` from the root layout:

```tsx
// app/_layout.tsx
import { useMigrations } from "drizzle-orm/expo-sqlite/migrator";

import { db } from "../../db/client";
import migrations from "../../db/migrations";

const RootLayout = () => {
    const { success: schemaReady, error: schemaError } = useMigrations(db, migrations);
    if (!schemaReady) return null; // splash stays visible
    // ...
};
```

`drizzle-kit`'s default generated `migrations.js` uses `babel-plugin-inline-import` to load `.sql` files at bundle time. Two ways to handle that:

- **Add the plugin** — wire `babel-plugin-inline-import` into `babel.config.js` and use the generated file as-is. Lower friction per migration, one extra plugin.
- **Hand-curate `db/migrations.ts`** — re-export the journal from `drizzle/meta/_journal.json` and inline each `<idx>_<tag>.sql` as a template literal. Zero babel plugins, but every new migration needs a manual paste from the generated SQL.

Pick one and stick with it. Hand-curating is fine for a single solo developer; teams should use the plugin to avoid merge conflicts in the inlined SQL.

## Live queries

For a **single-table** read, Drizzle's built-in is enough:

```ts
import { useLiveQuery } from "drizzle-orm/expo-sqlite";

const { data } = useLiveQuery(db.select().from(items));
```

It re-runs the query when the listed table changes.

**Caveat**: `useLiveQuery` only listens to the query's *primary* table. Cross-table joins (items filtered via a many-to-many join table; an item's collection memberships) won't refresh when *only* the join table changes. For those cases, listen to every relevant table explicitly:

```ts
// src/db/live.ts
import { addDatabaseChangeListener } from "expo-sqlite";
import { useEffect, useState } from "react";

export const useLiveTables = <T,>(
    queryFn: () => Promise<T>,
    tables: string[],
    deps: unknown[] = [],
): { data: T | undefined; error: Error | undefined } => {
    const [data, setData] = useState<T | undefined>();
    const [error, setError] = useState<Error | undefined>();

    useEffect(() => {
        let alive = true;
        const run = () =>
            queryFn()
                .then((d) => alive && setData(d))
                .catch((e) => alive && setError(e instanceof Error ? e : new Error(String(e))));
        run();
        const sub = addDatabaseChangeListener(({ tableName }) => {
            if (tables.includes(tableName)) run();
        });
        return () => {
            alive = false;
            sub.remove();
        };
        // eslint-disable-next-line react-hooks/exhaustive-deps
    }, deps);

    return { data, error };
};
```

Usage:

```ts
const { data: items } = useLiveTables(
    () => db.query.items.findMany({ with: { media: true } }),
    ["items", "media"],
);
```

The `deps` array is intentional — query parameters (a search string, a selected filter) should go there so the closure picks them up. The disabled-rule comment is load-bearing because `queryFn` is a fresh closure each render but only `deps` should retrigger.

## Common pitfalls

- **Forgot `enableChangeListener: true`** → live queries look stuck. No error is raised; reads just never refresh.
- **Forgot `PRAGMA foreign_keys = ON`** → `onDelete("cascade")` is a no-op. Test cascades after wiring a new schema.
- **Schema edit without a migration** → next launch fails on a missing column. Always `drizzle-kit generate` immediately, and add the new file to `db/migrations.ts` (or rely on the babel plugin) in the same commit.
- **Heavy joins on the render path** → wrap them in `useLiveTables`, which only re-runs on actual table changes, instead of recomputing in component bodies.
- **Mixing Zustand and the DB for the same data** → pick one source. The DB is canonical for relational data; Zustand is for client UI state (selected filter, picker open). Don't mirror DB rows into a Zustand store.

## When to layer React Query on top

If the local DB is just a cache of remote data, React Query can wrap reads/writes: `queryFn` reads from SQLite, mutations write to SQLite + call `queryClient.invalidateQueries`. Live queries become unnecessary in that mode — React Query owns refresh. Pick this **only** if the app actually syncs with a server; for offline-first apps with no remote, stay on `useLiveQuery` / `useLiveTables`.

## Migrating from AsyncStorage / a JSON blob

Reading an existing JSON-blob "store" once at boot and writing it into SQLite is a common one-shot. Patterns that help:

- Gate the migration on an idempotency check (e.g. "any rows in `items`? skip"). The legacy key may persist across an interrupted run; you don't want to double-insert.
- Wrap inserts in `db.transaction(async (tx) => { ... })` so a mid-flight crash doesn't leave half a library behind.
- Clear the legacy key only **after** the transaction commits. If clearing fails, the next boot re-runs cleanly thanks to the idempotency check.
- Keep the dependency around for that single read path until you're confident every active user has upgraded. Then drop both the migration code and the dependency in one commit.
